# Independent pre-build review — Deep Research Mobile App

Reviewer: independent second-pass audit (model-based, single perspective set, no separate human panel). Date: 2026-09-16. Inputs actually inspected: `Deep_Research_Reviewed_Build_Kit.zip` (extracted, 52 files including the standalone patch), `Deep_Research_Aggressive_Review.md`, `Deep_Research_Complaint_Evidence.csv`, `Grok_Code_Deep_Research_Goal.md`.

## Verdict

**Ready to start the bounded P0 baseline, with the named prerequisite corrections below.** Not ready to invite real users or claim a competitive advantage — both require evidence this kit explicitly and correctly says does not exist yet.

This kit is unusually disciplined for a pre-code specification package. It is not “impressive-sounding components.” Three checks that could have exposed dishonesty came back clean:

1. I ran `scripts/validate_review.py --check-manifest` and the unit tests myself. Results matched `EXECUTION_LEDGER.md` and `verification/VALIDATION_RESULTS.json` exactly (42 sources, 18 observations, 90 acceptance IDs, 12 draft eval cases, 9/9 unit tests passing, exit 0).
1. I byte-diffed `research/USER_COMPLAINTS.csv` against the raw `Deep_Research_Complaint_Evidence.csv` you attached separately — identical. The evidence ledger was not silently edited between the two artifacts.
1. I spot-checked five external citations (S28–S31, S34) against the live web: OpenRouter’s ZDR documentation, the OpenAI “harness engineering” post, and arXiv 2601.08536 (“DeepResearch Bench II”) all exist and say what the kit claims they say — including the specific caveat that OpenRouter’s ZDR setting does *not* cover plugins/tools like web search, which the kit’s `docs/SECURITY_PRIVACY_COST.md` already states correctly.

The earlier aggressive review’s own conclusion — “the architecture is broadly sound; the real risk is unproven research advantage, not the stack” — survives my scrutiny. I did not find a foundational engineering flaw. I found one real execution risk in the build prompt (below), a few small specification gaps, and several places where the kit’s self-criticism (F01–F14) is already resolved in this revision’s own text, which is worth confirming explicitly rather than re-litigating.

## What I did not inspect

No application repository was supplied or identified — I did not search for one myself (out of scope for this document review), so I cannot rule out that one exists elsewhere. I did not open every one of the 42 sources in `research/SOURCES.json`, the 18 complaint URLs, or all 90 acceptance-test cross-references; I sampled claims with the highest downstream impact (see `CLAIM_VERIFICATION.csv`). I did not run the proposed `pnpm` commands — none are implemented, and the kit is honest that they aren’t. I did not attempt to reproduce any of the 18 complaint incidents.

## Retained decisions (survive scrutiny, keep as-is)

- **Modular monolith, one backend codebase, separate API/worker entrypoints, Postgres as source of truth, relational (not graph) dependency edges.** ADR-001/002 give a real reversal condition and a real objection each, not just a preference. This is the correct starting complexity for a pre-revenue product with one engineer/agent.
- **Revision-fenced publication (`RevisionBasis`: briefRevision, evidenceRevision, consentEpoch, cancellationEpoch, workerLeaseFence).** This is the single most important mechanism in the kit — it is what prevents J06/J07/V2-07/V2-08 (stale-worker publication, cancel-during-writing races) from becoming real incidents. It is specified concretely enough to implement directly.
- **Privacy deletion overrides historical-report immutability (ADR-006).** I checked this specifically because F06 in `docs/CURRENT_STATE_AUDIT.md` flags it as an unresolved “textual tension” in the *original* kit. In this revision, `specs/ACCEPTANCE_TESTS.md` R19 and `specs/ENGINE_CONTRACTS.md` §7’s “private source deleted” row already state the resolution correctly (tombstone + purge/redact, no immutability exception). **The fix is already applied, not just promised.** Confirm this in `HANDOFF.md` so a future engineer doesn’t “re-fix” an already-fixed item.
- **Complaint evidence is honestly scoped.** `research/COMPLAINT_TO_REQUIREMENT.md` explicitly says 18 self-selected forum posts, mostly Jan–Mar 2026, are not population prevalence and are “hypotheses informed by published observations, not diagnoses of proprietary systems.” That is the correct epistemic posture for this evidence class; I would not ask for more hedging here, I’d ask for the real user tasks `HANDOFF.md` and `EVALUATION.md` already say are required before P1.
- **The document/data validator is real and does what it claims**, nothing more. It checks manifest integrity, ID uniqueness, cross-references, and command-status honesty — not application behavior. `docs/CODEBASE_GOVERNANCE.md`‘s closing line (“Do not report `pnpm verify` working because this review’s Python validator passed”) correctly forecloses the most likely way this tool gets misused later.
- **OpenRouter/retrieval capability honesty (ADR-003, ENGINE_CONTRACTS §4/§13).** Correctly refuses to promise a hard dollar cap on a route that can’t bound its own hidden search calls, and correctly gates `extract_table`/`inspect_visual` behind real adapters instead of letting the model claim it read a scanned table.

I looked hard for a severity-High or -Critical defect in the engine contracts, security model, or architecture themselves (the aggressive review’s own §6 scenarios A–J) and did not find one that isn’t already handled. Scenario D (paid-request timeout, unknown outcome) is handled by `outcome-unknown` state + conservative reconciliation (ENGINE_CONTRACTS §9). Scenario H (malicious webpage requesting a tool/budget increase) is handled by “runtime tool permissions cannot be expanded by source content” plus the S01/S36 injection controls. Scenario C (deletion during retry) is handled by consent/cancel epochs + tombstones (ADR-006, V2-09). I do not think this reflects incomplete adversarial thinking on the reviewer’s part so much as a genuinely well-covered specification — the honest scorecard is that P0’s *hardest* correctness work (concurrency, fencing, privacy-vs-retention) is well-specified, and P0’s *easiest*-sounding work (an actual runnable Postgres+worker loop) is what remains completely unstarted.

## Simplifications

1. **Do not build the six runtime roles as six separate LLM calls at P0.** `agents/runtime/CONTRACT.md` already says this (“Start with one planner/investigator controller and writer plus deterministic publication checks”), and I’d underline it: for the first vertical slice, one controller call plus deterministic verification code is sufficient to exercise every fencing/publication mechanism that actually matters. Splitting into separate calls per role adds latency and cost before there’s any evidence it improves output quality — exactly ADR-003’s own reasoning.
1. **Skip `extract_table`/`inspect_visual` entirely for P0.** They’re already gated as unavailable; there is no reason to stub them with fake success paths. A P0 slice that only handles digital PDF/text and discloses “unread” for scanned tables is a complete, honest, shippable slice.
1. **One retrieval route, one model route, no fallback chain, for P0.** ADR-003 and the “Latency and quality tradeoffs” section already say this. A privacy-compatible fallback is a P1+ concern (V2-20); building it before the primary route is proven is premature.

## Limitations of this review

- I did not have access to any application repository, so every conclusion about “what exists” is bounded by the four supplied documents plus what I could verify by web search in the time available.
- My external verification was a sample (5 of 42 sources, roughly checking the highest-impact ones — OpenRouter privacy behavior, the codebase-governance citation, and one benchmark citation), not an exhaustive re-audit; see `CLAIM_VERIFICATION.csv` for exactly which claims I checked and how.
- I did not run a red-team prompt-injection test, an SSRF probe, or any live security test — those require running code, which is out of scope for a document review and is correctly listed as not-yet-done in `EXECUTION_LEDGER.md`.
- I did not adjudicate whether the proposed research controller (P1) will actually outperform a simple iterative baseline — nobody can from documents alone; that is exactly what `EVALUATION.md`’s paired-task experiment is for, and it correctly has not been run.

## Return handoff

**Previous conclusions confirmed:** the architecture direction (ADR-001–006) is sound; the complaint evidence and competitor review are honestly scoped; the validator tooling does what it claims and nothing more; F01–F14 in `docs/CURRENT_STATE_AUDIT.md` are accurate characterizations of the pre-revision kit.

**Conclusions narrowed:** F04 and F06 are not still-open gaps in the *current* text — I verified the fixes are already present in `specs/ENGINE_CONTRACTS.md` §8–9 and `specs/ACCEPTANCE_TESTS.md` R19. Treat them as resolved-and-worth-a-status-note, not as remaining build work.

**Unresolved disagreements:** none of substance. The one place I’d push back hardest on the existing material is the Grok build prompt’s completion framing (PBR-01/02), which the aggressive review’s §10 charter asked me to check specifically and which I think deserves a concrete text fix, not just a general caution.

**Files/passages to change:** see `REQUIRED_CHANGES.md` for the prioritized list and `PROPOSED_REPLACEMENTS.md` for exact replacement text against `Grok_Code_Deep_Research_Goal.md`, `specs/SETUP_AND_HANDOFF.md`, and `specs/ENGINE_CONTRACTS.md`.
