## First implementation checkpoint — P0, not a polished shell
The first implementation session targets **P0**: one live, consented research request through API and durable worker, accessed evidence in real PostgreSQL, a bounded cited report, cancellation including writing, native close/reopen and source inspection, and one correction with revision-safe publication. This is the first checkpoint, not a promise it fits one session and not permission to claim the entire launch is complete. If P0 is verified and authorized capacity remains, continue the ranked plan; otherwise leave a precise checkpoint.

Do not build P3 decorative polish, a full settings/purchase/store flow, live push integration, or six separate runtime-role calls before the research loop works. **Minimum P4 governance, authentication/consent, authorization, cost reservations, deletion/cancellation fences, redacted diagnostics, basic accessible components and readable native input/report controls start in P0.** Safety and usable core controls are not later polish. P2's basic correction correctness also starts in P0; incremental-efficiency optimization comes later.

P0 has separate evidence gates, recorded individually in `verification/P0_ACCEPTANCE.json`:
- **P0-D — deterministic/local correctness:** run the established twelve smoke cases from `specs/ACCEPTANCE_TESTS.md` and applicable persistence/security cases. Use the actual selected PostgreSQL/queue implementation for transactional and recovery paths; deterministic model/retrieval fixtures are allowed here and explicitly labeled. These tests do not demonstrate real model quality.
- **P0-L — authorized live research:** exercise one real model route and one real retrieval route, save actual accessed evidence/citations and provider receipts, and test a bounded correction. Credentials, lawful access and spending authorization are required only where the selected route needs them. Passing fixture tests alone does not pass this gate.
- **P0-N — native lifecycle:** record the actual iOS and Android build/device environments and close/reopen/citation/correction results separately. A browser or CLI trace cannot pass a native gate. An unavailable platform remains blocked rather than guessed.

A local installed PostgreSQL/queue instance, including Docker Compose when available, can pass P0-D using declared versions, migrations and restricted credentials. It does not prove hosted Supabase authentication/RLS/storage, production connection-pool behavior, Render networking, or native/push/purchase integration. Those require their own checks before relying on them. Do not require cloud provisioning merely to test local transactions.

If a live or native gate is inaccessible, implement and test all unblocked P0 components and directly supporting work; retain the blocked gate and concrete missing input. Do not replace it with fake evidence or spend the blockage polishing an unrelated feature tree. The twelve smoke cases are necessary starting coverage, not sufficient evidence for all P0 invariants or public release. Parallel preparation of consented real-user tasks may begin now, but external recruitment/contact needs its own authorization.

## P0 — runnable, honest end-to-end baseline
**Finding/evidence:** F02/F04/F09/F10/F14; C02–C05; source/cancellation requirements in the original plan. **Use cases:** JOB-1/2 and all return journeys. **Status:** local application and durable execution implemented; current local/live/native evidence remains separately scoped in STATUS.md and verification/P0_ACCEPTANCE.json.
**Root cause addressed:** app lifecycle and provider visibility cannot be proven from prompts. **Behavior:** question -> consent/auth -> atomic admission -> real bounded evidence retrieval -> saved cited report -> close/reopen -> source inspection -> explicit correction. Preserve partial work and truthful failure states.
**Changes:** one backend codebase/API+worker, contracts, selected queue/storage/model/retrieval adapters, baseline evidence/report tables, simple native composer/reader. Implement publication fence, cancellation in writing and unknown-cost states immediately, not after visual polish.
**Alternative:** hosted opaque report alone is useful as a baseline but cannot satisfy invented passage/tool visibility. No need to connect five providers.
**Dependencies by gate:** P0-D needs an authorized workspace and real local PostgreSQL/selected queue; an existing repository or cloud credentials are not required to initialize authorized local work. P0-L additionally needs valid route credentials/access and a project budget where billable. P0-N needs each actual native build/device environment; do not assume every simulator run needs a paid store/signing account. Hosted deployment, purchases and live push have separate later credentials. No permission is inferred from another project.
**Benefit/tradeoff:** reliable delivery and measurable starting quality, at the cost of some boring infrastructure before novel research. **Acceptance:** original E/J/S essentials plus G01/G02; native G03 when tools available; actual receipts, persisted report and retrieval access fidelity. **Verification:** real PostgreSQL integration, provider probes, native reopen flow, not fixtures alone.
**Rollout:** local deterministic/database checks -> authorized capped live request and native lifecycle evidence -> later staged testing after relevant release/privacy gates. A live request is not authorization to invite real users. **Rollback:** disable live route, preserve accessible saved reports, keep auth/deletion/budget controls. **Priority/confidence:** launch blocker; high confidence in requirement, no implementation confidence claimed.

## Sequence and decision points
P0 and minimum P4 guardrails first. Conduct a small native usability pass and baseline task evaluation together. Add P1 only where diagnostics show an evidence/control failure. Deliver P2 correctness regardless of savings, but retain selective recomputation only when it beats full rerun safely. Complete P3 and operational release gates before public paid launch. P4 quality/cost evidence then determines expansion, not arbitrary calendar dates.

Reject near-term universal agent swarms, unbounded browser sessions, graph/vector services without evidence needs, generic permanent memory, social features, automated outbound actions, guaranteed exhaustive research and unsupported “best” marketing. Defer scheduled refresh and new connectors until actual return-use and cost/permission evidence exists.
